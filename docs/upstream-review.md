# 上游请求与 jmcomic 优化评估

核对日期：2026-11-06。范围：项目当前代码、安装目录中的 jmcomic 2.7.11 / curl_cffi 0.17.0 源码，以及下列官方文档。本次只增加评估文档，没有切换生产客户端或改变默认配置。官方 `latest` 文档中的能力均与安装源码交叉核对。

后续实施更新：个人账号密码加密持久化、查询/下载凭据同步、资料每次重新登录已经实现并完成真实账号只读测试；ARM 真实网络结果见 [实测报告](arm-benchmark-2026-11-06.md)。下文保留原评估时的发现；异步查询、DNS/TLS 共享和公平调度仍未实施，`advanced_retry` 插件与应用策略叠加也尚未提供兼容适配。

## 当前已经具备的能力

| 能力 | 当前实现与边界 |
| --- | --- |
| 常驻 Session | 默认 `curl_cffi_session`；查询和下载分开管理，跨请求复用，配置重载后等待旧任务释放资源 |
| 全局并发 | 最多 3 个作品下载、8 个查询任务；`JmSyncRuntime` 共用 3 个章节线程和 12 个图片线程，避免上游默认的层级线程池相乘 |
| 请求去重 | 相同查询和相同作品下载分别合并；成功查询缓存最多 1024 条，TTL 默认关闭 |
| 重试控制 | `NetworkPolicy` 使用同步客户端的 `domain_retry_strategy`；默认单次 HTTP 调用首次尝试加一次重试，多个域名共用预算；外层下载最多 3 轮，所有轮次共用 600 秒总时限 |
| 失败处理 | 按主机共享 429 冷却，解析 `Retry-After`；请求超时受剩余任务时限约束；缺失作品等永久失败不盲目重试 |
| 取消 | `DownloadControl` 协作取消，线程实际退出后才释放额度和同作品互斥 |
| 本地复用 | 已验证的 PDF 热缓存无需访问上游；下载流程沿用 jmcomic 的本地图片缓存 |

这些能力已在之前的实现和本地故障服务器测试中覆盖；先前 Docker 图片/PDF 性能测试没有测真实 JM 网络。本次没有新增真实上游性能数据。

## 建议的实施顺序

### 1. 先减少重复请求，并补齐登录和插件兼容性

现有配置已经支持以下设置；可以在接受数据短期过时的部署中启用，不需要替换网络库：

```dotenv
JMAPI_QUERY_CACHE_TTL_SECONDS=30
JMAPI_DETAIL_CACHE_TTL_SECONDS=300
```

搜索和分类共用前者，详情使用后者。仅缓存成功结果，缓存键包含规范化参数和运行时配置版本，重载时清空。对于反复查询相同参数的负载，这直接减少上游调用；并发但尚未完成的相同请求在 TTL 为 0 时也已经合并。

不建议直接用 `client.cache: true` 替代应用缓存。jmcomic 的同步客户端缓存使用字典，没有内置 TTL、容量限制或在途去重；长期运行时的数据新鲜度和占用更难控制。查询结果与下载内部实体目前也没有共享应用缓存；若继续整合，需要处理可变实体的复制、认证身份和配置版本，避免下载修改缓存对象。

核对源码还发现两处集成问题，应在迁移网络实现前修复：

- `load_runtime()` 先建立独立查询客户端；顶层 `auth` 的账号密码不会在 `new_jm_client()` 时自动登录。后续下载自动登录调用 `update_auth()`，其同步范围只有 `build_jm_client()` 缓存的下载客户端，既有查询客户端不在其中。因此带账号查询可能仍使用旧凭证。应在后台初始化阶段按需完成一次登录，再创建两类客户端，并为后续凭证更新建立明确同步机制；仍保留两个 Session。jmcomic 登录助手本身已有锁和幂等判断，不需要每次请求重新登录。
- `advanced_retry` 插件替换 `option.new_jm_client()`，无条件注入 `domain_retry_strategy=self`；应用也传入此参数。对安装源码的插件方法进行隔离调用，已复现 `TypeError: ... got multiple values for keyword argument 'domain_retry_strategy'`。当前默认配置未开启该插件。需要明确策略归属并提供兼容适配或清晰的配置错误，不能同时堆叠两个重试策略。

登录辅助客户端、`after_init` 插件及域名发现还需要单独审计：它们可能在应用策略接管前建立客户端或直接请求，不能把普通下载请求的总时限保证自动推广到全部初始化网络调用。

### 2. 为同步客户端共享 DNS 和 TLS 会话缓存

curl_cffi 官方说明，同步 `Session` 默认每个线程使用独立 curl handle。稳定线程池让连接在线程内复用，但同一个 Session 并不意味着所有线程共享一个 TCP 连接池。

0.17.0 已提供线程安全的 `CurlShare(dns=True, ssl_session=True)`。可在同一运行时的 Session 创建阶段注入共享对象，减少跨工作线程重复的 DNS 查询和 TLS 握手成本。此优化尤其值得在多个线程访问相同主机时测试；它不会减少图片正文流量，也不保证在代理远端解析 DNS 时仍有同等收益。

实施要求：

- 保持 `use_thread_local_curl=True`，共享 DNS/TLS 缓存即可，不能开启跨并发线程的 `connect=True` 连接缓存共享。
- 共享对象由运行时持有，等待所有关联线程和 curl handle 释放后再关闭。仅在主线程调用 `Session.close()` 不能据此推断其他线程的 handle 全部释放。
- 在 Session 工厂层注入，保持用户显式的传输实现、代理、Cookie 和超时语义；不要把包含锁的运行时对象直接放进会被 jmcomic 深拷贝的 YAML 配置树。
- 不额外开启 curl_cffi 层的自动重试，其默认重试为 0；否则会与 jmcomic 和应用下载重试叠加。

### 3. 改善排队公平性和主机级流量调节

`JmSyncRuntime.multi_thread_launcher()` 会对整个输入立即 `executor.submit()`，然后等待全部 Future。当前图片线程数受到全局限制，但内部待执行图片队列仍可很长；较早提交的大章节可能排在后来小作品的全部图片之前。应用层 32 个独立任务队列并不限制该内部队列。

建议增加应用拥有的下载调度适配器：按作品保留有限在途窗口，轮转提交图片；继续使用独立的章节和图片池，避免在图片池线程内阻塞等待向同一池提交的任务。取消时清理未开始的任务，已经开始的任务仍按现有规则回收。不要修改依赖安装目录。

网络限流还可在现有 429 冷却上增加：

- 按主机区分 API 与图片 CDN 的吞吐和失败率；连续连接失败时短期熔断，冷却结束用有限探测恢复，避免大量并行请求重复撞击坏域名。
- 对 5xx、连接失败增加有界退避和抖动；当前 HTTP 内层重试会立即进行，外层下载轮次才有异步退避。退避必须计入总时限并响应取消。
- 对单主机设置并发/速率上限，再根据成功率和 429 逐步调整。主机切换不能用来绕过账号或 IP 级限流；不能据不同域名推断它们是独立额度。

全局图片线程建议先保持 12，用相同负载比较 6、12、18；选择满足响应时间且失败率、429、CPU、RSS 均稳定的档位。只增加线程可能耗尽带宽、挤占解码资源并增加重试。

### 4. 原生异步优先从查询开始实验

jmcomic 2.7.11 已有 `new_jm_async_client()`、`download_album_async()`、`JmAsyncRuntime`。官方异步指南报告其基准中下载快 10% 以上、纯查询快 30% 以上；这是上游基准结果，并非本项目的测量或承诺。只修改 `async_impl` 配置不会自动切换当前同步调用。

查询先迁移的原因是边界小：搜索、分类和详情可共用应用生命周期内的异步客户端，由 curl_cffi `AsyncSession` 在同一事件循环内复用连接，减少网络等待占用的线程。必须同时保留现有去重、TTL、独立额度和配置代际生命周期。

不能直接把现有调用改为 `await` 后就上线：

- 当前异步客户端明确拒绝 `domain_retry_strategy`。其 `_request_with_retry()` 仍按“重试轮次 × 域名列表”尝试，没有接入本项目的 429 冷却和总预算策略；需要专门的异步适配层。
- `JmAsyncRuntime` 管理解码执行器，不提供所有下载共享的 HTTP 并发额度。异步下载器的图片/章节信号量是每个实例一份，必须另加应用级限制。
- 每个 `JmAsyncDownloader.__aenter__()` 新建客户端，退出时关闭；直接逐作品调用异步下载并不自动获得跨作品的长连接复用。
- 异步下载器会为整章图片创建任务，信号量限制执行并发但没有给等待任务数设置容量；仍需要窗口和公平性设计。
- 异步 Session 工厂只挑选部分配置字段传递；需逐项验证显式代理、环境代理、Cookie、HTTP 版本、超时和其他用户传输参数，不能假设与同步路径完全一致。
- 图片解码与写盘继续由执行器完成；取消下载不能留下后台写入，配置重载和退出要等待清理。

同步路径作为对照和回退。查询路径验证通过后，再评估让下载适配器拥有长驻异步图片客户端与共享的解码池。

## 不建议直接开启的选项

- `photo_concurrent_fetcher_proxy`：它能并发单章节详情关联的请求，但整本下载已经持有 album，`check_photo()` 会以 `fetch_album=False` 补详情，因此不能按每章都省一次 album 请求估算收益。代理还会另建执行器；须接入生命周期、上下文、限流后才能使用。
- 强制 HTTP/3 或切换网页端：实际收益依赖上游支持、代理及访问地区。安装版本默认客户端是 `api`，文档中的 `impl: html` 是配置示例；不能把示例当成当前运行默认值。
- 传输层通用响应缓存：保留应用已理解的查询结果缓存和图片缓存即可，避免对登录态或动态接口引入第二套不透明的缓存。

## 对比与验收

新增优化分别开关测试，不同时叠加后只看总耗时。保持相同 CPU/内存限制、代理、请求并发、图片集与账号配置。

| 场景 | 需要记录的结果 |
| --- | --- |
| 重复查询，缓存关/开 | 实际上游调用次数、命中率、p50/p95、结果新鲜度 |
| DNS/TLS 共享关/开 | 新建连接与握手次数、DNS/连接/TLS/首字节耗时、总耗时；先检查现有指标和 curl timing 的可采集范围 |
| 同步/异步查询 | 固定单次请求数和并发 1/8/20，比较吞吐、p95、线程数和总 RSS |
| 大作品与小作品混合下载 | 小作品等待时间、全局与单主机并发峰值、在途/排队任务数 |
| 429、坏域名、5xx、慢响应 | 重试实际次数、退避、恢复、截止时间和取消后的资源回收 |
| 登录、重载、退出 | 两类客户端凭证一致；失败重载回退；旧 Session/共享缓存清理无泄漏 |

离线服务器验证协议和故障行为；真实 JM 网络另行联调，每组至少 5 轮、报告中位数和 p95，同时记录请求数、429 和失败率。不要用前次 PDF 编码或 Base64 的 Docker 结果替代上游网络结论。
