# Docker 原版与优化版实测：2026-11-05

已完成三轮真实 Docker 对比。最新网络并发镜像的热 PDF、Base64、持续并发健康响应和 500 页预热重建均优于同轮原版；首次构建和 100 页重建仍较慢，不能认定全部性能改造都已验收。

## 网络并发改造后的最新容器复测

用户再次重建优化版后，顺序运行 `compare.py`、`verify_live.py` 和 `verify_network.py`，使用相同离线数据与容器限制。预热数据每组五次，冷构建各一次；持续并发健康样本每版 100 次。

| 测量 | 同轮原版 | 最新优化镜像 |
|---|---:|---:|
| 100 页冷构建 | 0.674 s | 1.733 s |
| 100 页重建，中位数 / p95 | 0.678 / 0.715 s | 0.792 / 0.808 s |
| 500 页冷构建 | 3.246 s | 6.350 s |
| 500 页重建，中位数 / p95 | 3.307 / 3.318 s | 2.376 / 2.481 s |
| 100 页热 PDF，中位数 / p95 | 34.09 / 35.23 ms | 15.61 / 17.03 ms |
| 500 页热 PDF，中位数 / p95 | 168.47 / 210.93 ms | 69.62 / 70.70 ms |
| 10 MiB Base64，中位数 / p95 | 61.44 / 63.22 ms | 13.94 / 14.23 ms |
| 100 MiB Base64，中位数 / p95 | 757.41 / 778.64 ms | 121.31 / 121.99 ms |
| Base64 100/10 MiB 采样 RSS 增量 | 494.36 MiB | 0 MiB |
| 500 页重建，父子进程峰值 RSS | 438.41 MiB | 241.09 MiB |
| 500 页重建，峰值线程数 | 8 | 9 |
| 持续 20 并发，健康请求中位数 / p95 / 最大值 | 673.55 / 1014.02 / 1172.39 ms | 0.71 / 1.18 / 1.61 ms |

同轮对比，优化版 500 页预热重建耗时降低约 28%，500 页热 PDF 降低约 59%，100 MiB Base64 降低约 84%。与上一轮优化镜像相比，Base64 单请求从约 108 ms 增至 121 ms；分块编码调度与发送并发隔离增加了开销，换来了慢客户端隔离。不同轮次存在运行环境波动，不能把跨轮差值全部归因于代码。

两版持续并发均无请求错误；原版在 16.55 s 内完成 308 个数据请求，优化版在 1.33 s 内完成 104 个。测试以完成 100 次健康探测结束，持续时间不同，不将请求数作为等时吞吐量比较。优化版健康 p95 和 Base64 内存增量均达到计划目标。

内容验证通过：10/100 MiB Base64 SHA-256、中文名称、Content-Length、原始 PDF 与 Base64 一致、分片与页数、加密解密、规范化 ID 和非法 ID 422；两版完整 PDF 与分片的首/中/末页抽样像素摘要一致。真实 JM 网络未参与本轮容器测试，HTTP 重试、连接复用和 429 仍由本地故障服务器测试覆盖。

慢客户端场景在实际优化版容器上验证：三个 100 MiB 请求保持连接但停止读取，第四个 10 MiB Base64 请求在 23.39 ms 内完成解码摘要校验，此时三个慢请求仍持有各自发送名额。四路全部占满时，第五路进入等待；关闭一路后恢复完成，其他三路仍保持活动。原始 PDF 的 ETag / Last-Modified 条件请求返回 304，Range 返回 206 且字节正确。

单独保留一个不读取数据的连接，默认 30 秒发送阻塞超时在 30.22 秒触发，超时计数增加，活动发送名额回到零，随后健康接口返回 200。上述场景顺序执行，结束后测试连接全部关闭。

最新原始数据在 `benchmark-results/network-fixed/`；本节优先于下方历史轮次。网络并发测试脚本只新增到宿主机测试工具，不改变容器内服务源码。

## 缓存扫描修正后的容器复测

用户重新运行启动脚本后的真实容器测量，预热组各重复五次。此次镜像包含缓存扫描修正，尚未包含随后新增的网络重试和发送并发改造。

| 测量 | 同轮原版 | 修正后的优化镜像 |
|---|---:|---:|
| 100 页冷构建 | 0.790 s | 2.503 s |
| 100 页重建，中位数 / p95 | 0.690 / 0.702 s | 1.112 / 1.303 s |
| 500 页冷构建 | 3.369 s | 7.720 s |
| 500 页重建，中位数 / p95 | 3.415 / 3.504 s | 3.408 / 4.326 s |
| 100 页热 PDF，中位数 | 34.32 ms | 15.33 ms |
| 500 页热 PDF，中位数 | 166.10 ms | 66.26 ms |
| 100 MiB Base64，中位数 | 710.43 ms | 107.77 ms |
| Base64 100/10 MiB 采样 RSS 增量 | 498.50 MiB | 0 MiB |
| 500 页重建，父子进程峰值 RSS | 440.55 MiB | 240.39 MiB |
| 持续 20 并发，100 次健康探测 p95 | 903.12 ms | 1.14 ms |

500 页重建由首轮的 7.312 s 降至 3.408 s；跨轮比较仅用于定位退化，同轮原版 3.415 s 是更合适的性能参照。父进程分配器保留内存会影响跨轮 RSS，不能只按 RSS 差值推导单次构建内存成本。

原始结果位于 `benchmark-results/cache-scan-fixed/`，包括重建后功能校验和 100 次持续健康探测；原始 PDF / Base64、分片、加密和两版抽样像素摘要一致性均通过。下面保留首轮明细。网络并发源码的默认配置、测试及待部署边界见 [优化说明](optimization.md) 和 [验证记录](validation.md)。

## 条件与测量方法

- 主机：AMD Ryzen 9 8940HX，Linux x86_64。两个容器各限制 2 CPU、2 GiB，Python 3.12，使用相同本地 Docker 卷。
- 原版：`feb1cc6` 原始源码和锁文件；优化版：用户本次启动的工作目录镜像，包含依赖升级，尚不包含测试过程中新增的缓存扫描修正。
- 固定数据：100/500 页，512×768 RGB 随机图片，种子 `20261105 + 页索引`，源 JPEG quality=90；PDF quality=70，JPEG optimize 开启，不加密。
- 每组记录一次冷构建；保留单页编码缓存并删除最终 PDF，重复重建五次；最终 PDF 热缓存再重复五次。重建耗时包含清单完整性检查、子进程和 HTTP 文件传输，冷构建另有首次单页编码成本。
- 使用 `compare.py`；独立进程每约 10 ms 读取服务父子进程的 RSS 和线程数。每次重置等待监控采样轮次确认，防止上一轮峰值混入。结果为采样峰值，可能漏掉极短峰值，不包含客户端内存。
- 另以 20 个持续数据请求工作线程发送 10 MiB Base64 请求，同时用 5 个探测线程完成 100 次健康请求。该测试独立运行，期间无本地编码压测。
- 离线夹具仅替换上游 I/O；PDF、分片、加密和响应均走真实公开接口。10/100 MiB 传输文件为稀疏文件，用于传输与内存测试，不用于 PDF 内容校验。

## 首轮容器结果

耗时为五次测量的中位数 / p95；冷构建和首次分片各测一次。p95 使用最近秩，五次样本时等于最大值。较小的值更好。

| 测量 | 原版 | 当前优化镜像 |
|---|---:|---:|
| 100 页冷构建 | 0.688 s | 1.961 s |
| 100 页重建 | 0.684 / 0.721 s | 1.102 / 1.324 s |
| 500 页冷构建 | 3.324 s | 9.894 s |
| 500 页重建 | 3.394 / 3.459 s | 7.312 / 8.094 s |
| 100 页 PDF 热缓存 | 34.02 / 35.29 ms | 14.61 / 15.00 ms |
| 500 页 PDF 热缓存 | 168.09 / 227.63 ms | 65.80 / 69.07 ms |
| 500 页作品的首个 100 页分片 | 0.666 s | 1.528 s |
| 10 MiB Base64 | 60.18 / 60.79 ms | 12.52 / 14.09 ms |
| 100 MiB Base64 | 729.97 / 745.66 ms | 108.29 / 111.18 ms |
| 500 页重建，父子进程峰值 RSS | 386.97 MiB | 243.68 MiB |
| 500 页热缓存，峰值 RSS | 657.20 MiB | 91.06 MiB |
| Base64 100 MiB 相对 10 MiB 的峰值 RSS 增量 | 498.54 MiB | 0 MiB（采样值） |
| 500 页重建，父子进程峰值线程数 | 8 | 9 |
| 500 页 PDF 大小 | 94,447,315 B | 94,440,815 B |

热 PDF 中位耗时降低约 57%（100 页）和 61%（500 页）；100 MiB Base64 耗时降低约 85%。优化版 Base64 的两个文件大小下采样峰值相同，符合 ≤16 MiB 增量目标；这不表示编码没有内存开销。当前镜像 500 页重建中位耗时为原版的 2.15 倍，需要修复后继续验收。

## 功能验证

两版均通过 10/100 MiB Base64 分块解码 SHA-256、中文文件名、Content-Length、100 页 PDF 的原始文件与 Base64 内容一致性、500 页作品的第二分片页数、500 页/5 分片布局、100 页加密解密、展示名称规则。完整 PDF 与分片抽取首/中/末页图片，跨版本尺寸和解码像素摘要一致。

原版的加密和非加密 PDF 路径存在冲突；优化版在 `v2/100/` 下分别保存，已实测独立路径。优化版五个作品接口非法 ID 均返回统一 422；`jM00100` 与 `100` 命中同一规范化路径。

## 已修正的源码与本地实验

性能剖析发现：500 页预热构建对单页缓存执行 500 次全目录回收扫描，约 250,000 次文件属性查询；该扫描在剖析中占 2.03 / 2.66 s。已改为每次构建统一校准缓存容量，缺失页原子写入后增量记账，超过配额才回收，并保留使用中页面的锁保护。

同一主机、同一数据、同一升级依赖下，直接调用编码合并函数、五次预热测量的中位数如下。它不包含接口完整性检查、子进程启动或 Docker 文件系统开销，不能与上表直接比较：

| 页数 | 扫描修正前 | 扫描修正后 |
|---|---:|---:|
| 100 | 0.0965 s | 0.0672 s |
| 500 | 1.3011 s | 0.3126 s |

新增测试确认预热构建仅扫描一次目录、不重复编码，以及容量记账、损坏账本恢复和使用中页面保护。Python 3.12/3.13 各 137 项测试通过，警告视为错误；Ruff、格式、mypy、锁文件和依赖检查通过。

本地关闭单页缓存，固定 quality=70，各预热后重复五次的 JPEG optimize 实验：

| 页数 | optimize 开启耗时 / PDF 大小 | optimize 关闭耗时 / PDF 大小 |
|---|---:|---:|
| 100 | 0.759 s / 18,890,160 B | 0.486 s / 19,633,535 B |
| 500 | 3.314 s / 94,440,815 B | 2.003 s / 98,157,255 B |

本样本关闭 optimize 的编码耗时降低约 36%–40%，文件增大约 3.9%；默认继续开启。该实验不是 Docker 内的开关对比。

## 复测与留存

缓存扫描和网络并发改造均已通过上面的离线 Docker 场景。未来更新优化版镜像时，原版和数据卷可以复用：

```sh
sudo docker compose -f compose.benchmark.yaml up -d --build --no-deps optimized
```

随后顺序运行 `compare.py`、`verify_live.py`、`verify_network.py`，并为新一轮选择新的报告目录，避免覆盖旧数据或让测量相互影响。命令详见 [运行步骤](docker-comparison.md)。镜像依赖安装层已与源代码层分开，方便后续重建。

原始 Docker 数据保存在 `benchmark-results/docker-2026-11-05-confirmed/{baseline,optimized,health-sustained}.json`，功能验证在 `benchmark-results/docker-2026-11-05/live-verification.json`。本地编码和 optimize 实验副本在确认目录下的 `local-encoding/`；`benchmark-results/` 不进入 Git，本文保存主要结果。
