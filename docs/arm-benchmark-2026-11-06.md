# ARM64 部署与真实上游实测（2026-11-06）

已通过 HexHub SSH MCP 在 Oracle Arm-3 原生构建、部署并完成原版与优化版对照。查询、并发响应和缓存复用有明显收益；真实冷下载加首次 PDF 构建慢约 8%，峰值容器内存降低约 54%。不能据此宣称所有场景都更快。

## 环境与方法

- Ubuntu 24.04.5 LTS，ARM64 Neoverse-N1，2 核、11927 MiB 内存；Docker 29.1.3、Compose 2.40.3。
- 两版均使用 ARM64 Python 3.12.16，每个服务限制 2 CPU、2 GiB，单进程；只绑定回环端口。
- 基线固定 `feb1cc60a58ebf6400a86bb6b2062d815e7855a2`；优化版为本地工作目录快照。没有把未提交代码遗漏在部署之外。
- 基线依赖：jmcomic 2.6.18、curl_cffi 0.15.0、pypdf 6.10.2、Pillow 12.2.0；优化版为 2.7.11、0.17.0、6.21.4、13.0.0。因此结果反映代码和依赖的总体变化，不能单独归因于 Session 或某一个优化。
- 源码归档 SHA-256：`88669a099f07c55a01b7f12b2a9d17c68b3aa88ace1834dfcb9b56e1e3e55082`。远端 `source-manifest.json` 保存归档内当前源码文件的摘要。
- 查询/下载性能对照使用匿名请求、无显式代理，两版 HTTP 重试均显式设为 1、超时为 `(3, 12)`；查询 TTL 均关闭。追加的真实账号只读实测单独记录，不混入匿名基准。
- 每组重复五轮，真实查询和下载交替两版顺序。五个批次的 p95 相当于最大值；查询请求 p95 则使用五轮内全部请求。
- 请求端运行在同一 ARM 主机，访问回环 API；真实网络段是 ARM 主机到 JM，不包含用户终端到 ARM 主机的公网延迟。

## 真实 JM 查询

共 590 个计入表格的查询请求，均为 HTTP 200，无应用失败；优化版未记录到 429。下表为每批全部请求结束的耗时中位数，括号为单请求 p95。

| 场景 | 原版 | 优化版 |
| --- | ---: | ---: |
| 单路详情 | 155 ms（197 ms） | 112 ms（106 ms） |
| 单路搜索 | 158 ms（162 ms） | 132 ms（127 ms） |
| 单路分类 | 226 ms（229 ms） | 197 ms（189 ms） |
| 8 路相同详情 | 307 ms（290 ms） | 117 ms（107 ms） |
| 20 路相同详情 | 584 ms（564 ms） | 124 ms（116 ms） |
| 8 路不同分类页 | 480 ms（510 ms） | 247 ms（250 ms） |
| 20 路不同分类页 | 918 ms（870 ms） | 590 ms（564 ms） |

批次耗时包含客户端同步启动、结果收集和健康探测循环，所以可能大于单请求 p95。20 路不同分类页的批次吞吐约为 21.8 → 33.9 请求/秒；这是该批次的请求数除以耗时，并非长期极限吞吐。

优化版 8/20 路相同详情每轮均只产生 **1 次**上游 HTTP 请求；不同分类页每轮分别产生 8/20 次。该收益来自在途去重，不依赖 TTL。基线没有上游请求计数指标，原始报告中的空计数表示未采集，不能解释为未访问上游。

## 真实冷下载

作品 ID `1488544`，52 页。两版各五次，每次创建全新的容器和 1 GiB tmpfs，确保服务端原图、PDF、单页编码缓存均为空；完成后回收该临时容器。请求为 `quality=70&passwd=false&pdf=true`。

| 项目 | 原版 | 优化版 |
| --- | ---: | ---: |
| 冷下载、解码、PDF 构建及发送中位耗时 | 13.82 s | 14.93 s |
| 上述耗时 p95 | 14.29 s | 15.23 s |
| 紧接着读取热 PDF 中位耗时 | 90.9 ms | 69.4 ms |
| 最大容器内存采样值 | 1692.7 MiB | 779.8 MiB |
| CPU 时间中位数 | 21.30 CPU·s | 22.04 CPU·s |
| 平均使用 CPU 核数中位数 | 1.54 | 1.48 |
| 100 ms 采样的最高 CPU 核数 | 1.91 | 1.87 |

10 次均校验到 52 张原图、52 页 PDF；同一次冷/热读取的 PDF 摘要一致。优化版每轮记录到 55 次成功上游 HTTP 请求。实时上游有部分图片字节摘要变化，不能把这组数据当成严格固定字节集；固定数据的编码对照见下一节。

这里测的是完整冷请求，不是纯图片网络传输速度。内存为整个容器的 cgroup `memory.current`，包括进程、tmpfs 文件和文件缓存，不能直接视为 Python 堆或 RSS。CPU 使用已经超过单核；单本 PDF 编码阶段仍主要使用一个核心。

首次尝试中，校验脚本误选了单页 PDF 中间缓存，未纳入这五轮。修正为使用 `/get_pdf_path` 返回的整本文件后重新完成全部下载。前次中断记录保留在远端 `results/download.json`，有效结果为 `results/download-confirmed.json`。

## 固定离线图片与 Base64

使用同一组 100/500 页、512×768 JPEG。预热重建保留单页编码缓存，删除整本/分片成品；热 PDF 直接重复读取。以下时间包含 API 请求与响应读取。

| 场景 | 原版 | 优化版 |
| --- | ---: | ---: |
| 100 页首次构建 | 1.81 s | 2.79 s |
| 100 页预热重建中位数 | 1.57 s | 1.14 s |
| 500 页首次构建 | 7.88 s | 9.64 s |
| 500 页预热重建中位数 | 7.55 s | 2.48 s |
| 500 页预热重建 p95 | 7.98 s | 2.81 s |
| 500 页热 PDF 中位数 | 806 ms | 384 ms |
| 500 页预热重建父子进程峰值 RSS | 322.6 MiB | 247.1 MiB |
| 500 页预热重建线程峰值（父子进程合计） | 8 | 9 |
| 500 页 PDF 大小 | 94,447,315 B | 94,440,815 B |
| 10 MiB Base64 中位耗时 | 210 ms | 46 ms |
| 100 MiB Base64 中位耗时 | 1.41 s | 442 ms |
| 10 → 100 MiB Base64 的峰值 RSS 增量 | 493.5 MiB | 0 MiB（采样值） |

RSS 每约 10 ms 采样，CPU/cgroup 内存每约 100 ms 采样；可能漏掉极短峰值。优化版 Base64 两组采样峰值均约 93.5 MiB，不表示编码没有分配内存。PDF 阶段平均约 1.05–1.11 核，包含同容器 RSS 监控进程。

另做持续 20 个客户端请求、5 个健康探测客户端、共 100 次健康探测：原版健康接口 p95 **1.741 s**，优化版 **3.51 ms**；均无请求异常。两版总测试时长不同，因为测试到固定探测次数后停止，不能直接比较完成请求总数作为吞吐。

10/100 MiB Base64 解码长度和摘要、整本 PDF、分片、加密与命名校验通过；两版固定图片中抽样的首/中/末页像素摘要一致。该校验不是对所有 PDF 页面的逐像素渲染检查。

优化版额外通过 304/Range、3 个停滞客户端并存时的快速响应、4 路发送上限和队列恢复。30 秒发送超时实测为 30.04 秒，随后额度释放且健康检查成功。
